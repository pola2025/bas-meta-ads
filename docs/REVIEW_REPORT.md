# 기획 문서 검토 보고서

**날짜:** 2025-11-19
**검토 문서:**

- `PROJECT_SPECIFICATION.md` (v1.1)
- `IMPLEMENTATION_GUIDE.md`

## 1. 종합 평가

기획 문서는 체계적으로 작성되었으며 BAS Meta Ads Analytics Platform의 핵심 요구사항을 잘 다루고 있습니다. 아키텍처(Supabase + Railway + Next.js)는 현대적이며 프로젝트 규모에 적합합니다. v1.1에 추가된 Job Queue (BullMQ)와 파티셔닝(Partitioning)은 안정성과 확장성을 크게 향상시킬 것으로 보입니다.

## 2. 강점

- **견고한 아키텍처:** 수집기(Collector)와 대시보드(Dashboard)의 관심사 분리, 그리고 API 속도 제한/재시도를 위한 Job Queue 사용이 훌륭합니다.
- **데이터베이스 설계:** `raw_data`에 대한 파티셔닝 적용과 집계 테이블(`weekly`, `monthly`) 분리는 성능을 고려한 잘된 설계입니다.
- **보안:** 토큰 저장을 위한 Supabase Vault 통합과 RLS 정책 적용은 강력한 보안 관행입니다.
- **자동화:** `pg_cron`을 통한 파티션 생성 및 토큰 갱신 자동화는 운영 부담을 줄여줍니다.

## 3. 갭(Gap) 및 개선 영역

### 3.1 테스트 전략

- **관찰:** 가이드에 "테스트 체크리스트"가 언급되어 있으나, 수동 검증에 크게 의존하고 있습니다.
- **위험:** 개발 중 자동화된 테스트 없이는 회귀 버그(Regression bugs)가 발생할 수 있습니다.
- **권장사항:**
  - 핵심 로직(예: `generate_weekly_summary`, 데이터 변환)에 대한 **단위 테스트(Unit Tests)** (Jest/Vitest) 추가.
  - 주요 사용자 흐름(로그인 -> 대시보드 -> 상세)에 대한 **E2E 테스트** (Playwright) 추가.
  - `package.json`에 `test` 스크립트 정의.

### 3.2 CI/CD 파이프라인

- **관찰:** 배포 지침이 수동이거나 Vercel/Railway의 Git 연동에 암묵적으로 의존하고 있습니다.
- **위험:** 배포 과정의 일관성이 떨어지거나 배포 전 검사가 누락될 수 있습니다.
- **권장사항:**
  - 다음을 수행하는 **GitHub Actions** 워크플로우 생성:
    - 린팅(Linting) 및 타입 체크(Type Checking).
    - 테스트 실행.
    - 병합(Merge) 시 스테이징/프로덕션 자동 배포.

### 3.3 에러 모니터링 및 알림

- **관찰:** `producer_errors` 테이블이 존재하고 일부 실패에 대한 텔레그램 알림이 언급되어 있습니다.
- **위험:** 텔레그램 API가 실패하거나 로그를 확인하지 않으면 실패가 조용히 넘어갈 수 있습니다.
- **권장사항:**
  - 백엔드와 프론트엔드 모두에 **Sentry**와 같은 전용 에러 트래킹 도구(무료 티어 활용 가능) 통합 고려.
  - "Dead Letter Queue" 알림이 중요하게 다뤄지도록 하고, 가능하다면 다중 채널로 알림을 받도록 설정.

### 3.4 타입 안전성 및 타입 공유

- **관찰:** 백엔드(Node.js)와 프론트엔드(Next.js)가 분리되어 있는 것으로 보입니다.
- **위험:** API 응답과 프론트엔드의 기대치 간에 타입 불일치가 발생할 수 있습니다.
- **권장사항:**
  - **Supabase CLI**를 사용하여 데이터베이스 스키마에서 TypeScript 타입을 자동으로 생성 (`supabase gen types`).
  - 이 타입들을 백엔드(TS로 전환 시)와 프론트엔드 간에 공유하여 일관성 유지.

### 3.5 로컬 개발 환경

- **관찰:** 로컬 개발 시에도 클라우드 서비스(Upstash, Supabase)에 의존합니다.
- **위험:** 인터넷 의존성 및 과도한 개발 사이클로 인한 잠재적 비용/지연 발생 가능성.
- **권장사항:**
  - 완전한 오프라인 개발 환경을 위해 로컬 Redis 및 PostgreSQL(Supabase Local Dev)을 위한 `docker-compose.yml` 제공.

## 4. 보완을 위한 구체적인 실행 항목

1. **`package.json` 명세 작성:** 정확한 의존성과 스크립트 정의.
2. **`.env.example` 초안 작성:** 필요한 모든 환경 변수를 한곳에 정리.
3. **Supabase 타입 생성 설정:** 타입 동기화를 위한 스크립트 추가.
4. **에러 핸들링 구체화:** 가이드에 Sentry 설정 단계 추가.

## 5. 결론

이 계획은 MVP 및 그 이후를 위해서도 견고합니다. 테스트 및 CI/CD 관련 갭을 해결하면 프로젝트의 장기적인 유지보수성이 크게 향상될 것입니다.
